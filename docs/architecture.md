## 2. 关键设计判断（很重要）

### 2.1 录像不解码，直接存原始码流
196 路如果每路都解码，RK3588 的 VPU 扛不住。NVR 的核心事实是：**录像只需要接收并落盘压缩码流（remux），不需要解码**。
- 196 路 × ~4Mbps(H.265) ≈ **784 Mbps ≈ 98 MB/s** 写入，分摊到多块盘完全可行。
- 只有"预览 / AI 分析"才需要解码，且只解码正在看的/正在分析的少数通道。

### 2.2 分层解码预算（RK3588 VPU/NPU 有限，必须调度）
- **预览**：Web 4 用户 + 本地 LVGL 屏。只解码当前画面里的通道（如 4/8/16 分割）。
- **AI（人形/移动）**：用摄像头**子码流**（低分辨率）做分析，NPU 跑 RKNN。196 路同时做人形检测不现实 → 采用**轮询调度 + 优先用摄像头端事件**（ONVIF 事件 / GB28181 报警）来触发，NVR 侧只对重点通道做二次确认。⚠️ 这块策略需要和你确认。

### 2.3 WebRTC 与 H.265 的坑
- 浏览器对 **H.265 WebRTC 支持很差**（基本只有 Safari 部分支持）。Web 预览要稳，需要把 H.265 → **H.264 转码**（RK3588 硬编码 H.264）再走 WebRTC；或推送 H.264 子码流。
- 建议：**Web 预览统一用 H.264 子码流 / 转码流**，录像仍存原始（H.264/H.265）主码流。

## 2.4 单摄像头处理流水线（依据你的数据流图，每方块=1线程）

```
IPCAM ──VIDEO──┬── H.264/265 DATA MAIN ──[数据分发]──┬── RECORD_MAIN(+AUDIO_AAC1) ──[RING BUFFER 预录像]── HARD DISK
               │                                      ├── DECODER_MAIN ── PREVIEW_MAIN VIDEO/AUDIO(AUDIO_DEC1)
               │                                      ├── RTSP1_MAIN(+AAC2)
               │                                      ├── RTSP2_MAIN(+AAC3)
               │                                      ├── RTSP3_MAIN(+AAC4)
               │                                      └── RTSP4_MAIN(+AAC5)
               │
               └── H.264/265 DATA SUB ──[数据分发]────┬── DECODER_SUB ── PREVIEW_SUB VIDEO/AUDIO(AUDIO_DEC2)
                                                       ├── RTSP1_SUB(+AAC6)
                                                       ├── RTSP2_SUB(+AAC7)
                                                       ├── RTSP3_SUB(+AAC8)
                                                       └── RTSP4_SUB(+AAC9)
IPCAM ──AUDIO──[数据分发]── AAC DECODER ──[数据分发]──┬── AUDIO_DEC1
                          (原始 AAC1~9 分发)          └── AUDIO_DEC2

回放：HARD DISK ──┬── H264/265 DECODER ── PLAY VIDEO
                 ├── AAC DECODER ── PLAY AUDIO
                 └── RTSP1~4_PLAY (AUDIO+VIDEO, 4 客户端)
```

**线程模型确认**：你的设计是"每方块=一个线程"，单摄像头约 20+ 线程 → 196 路会到 ~4000 线程。
- **轻量线程（I/O 型）**：数据分发、RECORD_MAIN、RTSP 转发。这些只搬压缩数据，不解码，线程多也 OK（但要用**线程池/epoll**，不能真的裸开 4000 个内核线程，否则调度开销和内存吃不消）。→ 建议：分发/转发用**少量工作线程 + 事件驱动**，逻辑上保持"每方块一个执行单元"，物理上复用线程池。
- **重量线程（DECODER_MAIN/SUB）**：**已确认按需开**。只有该通道在本地 UI/Web 被预览、或被 AI 抽帧分析时才起解码线程，切走就释放。避免 196 路常开压垮 VPU。
- **RTSP 输出（主4+子8=每路8路）**：只在有客户端连接时才推流，空闲不占资源。

**WebRTC 落点**：你图里 Web 预览用的是 RTSP 输出，WebRTC 网关从 RTSP1_MAIN/SUB 拉压缩流转 WebRTC（H.265 需转 H.264）。4 用户 = 复用这 4 路 RTSP 输出。

## 2.5 全局 Ring Buffer + 顺序存储（关键存储设计）

**你的要求：所有通道数据进同一个 ring buffer，顺序存储。** 这是经典高性能 NVR 做法：

- 196 路如果各写各的文件 → 磁头狂跳、随机 I/O、碎片化，机械盘扛不住。
- 正确做法：所有通道的码流帧先汇聚进**一个全局 ring buffer**，按到达顺序打包成**大块(如 1~8MB block)**，**顺序追加**写入磁盘（裸盘或大容器文件），把随机写变成顺序写，跑满 HDD 带宽。
- 另用**索引库(SQLite/自研索引)**记录每帧/每段的位置：`(通道号, 时间戳, GOP 关键帧) → (磁盘号, block 偏移, 长度)`，回放时按索引定位。
- Ring buffer 同时天然实现**预录像**：事件发生时，缓冲区里已有事件前 N 秒的数据可一起落盘。

## 2.6 磁盘管理方案（依据你的第二张图，已确认）

**落盘顺序**：写满一个盘，再顺序往下一块盘写（10 块盘串成一个大顺序空间，写满回绕覆盖最旧）。

**格式化 / 初始化流程**：
```
启动 → 已经格式化? ──否──→ 格式化选定盘:
                              1) 分区：每 900G 一个分区(逻辑盘)
                              2) 快速格式化
                              3) 每个逻辑盘生成固定 1G 的 log.txt
                              4) 专用线程在每个逻辑盘预生成 A001,A002... 每个 1GByte
                                 (预分配，避免开文件等待影响即时录像)
      → 已格式化? ──是但异常──→ 修复硬盘
```

**存储介质**：ext4/xfs 上用**预分配 1GB 大文件**（A001, A002, ...）顺序写；每个逻辑盘一个 `log.txt`（固定 1GB）当索引/日志。

**log.txt 日志格式（固定字长行，已确认）**：
```
A003_CH18_2026_01_26_15:20:30_10_A/M/P/T
 │    │        │              │   └─ 录像类型: A=IO报警 M=移动报警 P=人形报警 T=定时录像
 │    │        │              └─ 该秒内第几个 I 帧(一秒可能多个 I 帧, 一般为 1)
 │    │        └─ 时间戳
 │    └─ 第 18 路视频通道
 └─ 数据文件名(A003)
```
- **日志与录像数据同步覆盖**：每覆盖一个录像文件，就更新/清空对应那条日志。
- **log.txt 硬约束（重要）**：每条记录**定长**；**只能"修改"或"清空"记录，绝不"删除"记录**（不改变行数/文件大小）。文件**固定大小**，避免长时间运行后文件散乱、效率骤降。
- **end 标记（滚动写）**：**每记录一个 I 帧就写一条 log 行、并在该行带上 `end` 标记，同时清除上一行的 `end`**。因此 `end` 始终跟在"最新写入的那条 I 帧记录"后面 → 重启时靠 `end` 定位写指针。日志行定长，便于原地覆盖上一行的 end。

**录像写入**：所有通道数据**先到先存**（全局 ring buffer 汇聚 → 顺序写入当前 1GB 文件，满了换下一个文件/逻辑盘）；**每个 I 帧记录其文件内位置**，供 seek。

**回放**：多线程顺序扫描各盘 `log.txt`，按 `(通道, 时间, 类型)` 检索定位，按 I 帧位置 seek 回放。

**启动录像**：开多线程顺序查找各盘 `log.txt` 的 `end` 标记，恢复写指针后继续 first-come-first-served 存储。

**全局唯一 end 位置（重要）**：每次启动，除了修复硬盘，还要确定**全局唯一的 end 写指针**。
- 虽然每个逻辑盘都有 `log.txt`、都可能带 `end` 标记，但**整机只认一个 end**：取**最靠近初始逻辑盘**的那个 `log.txt` 的 end 位置作为当前写指针。
- 原因：用户可能从**另一台 NVR** 拆一块盘插进来，那块盘的 `log.txt` 里也有它自己的 `end`（外来/陈旧的），不能被它误导。按"最靠近初始逻辑盘"的规则选，保证从本机正确的续写点接着写。
- **逻辑盘顺序（已确认）**：直接用 **Linux 自动排列的硬盘顺序**（如 /dev/sda,sdb...），不特殊处理外来盘；但**必须识别每个盘/逻辑盘是否已格式化**（未格式化的走格式化流程，不参与写入）。

**end 校准 & 去重（上电恢复细节，重要）**：
- 上电找到 end 位置后，**还要再扫 `log.txt`，检查该行的前一行/后一行是否也有 end 标记**（异常掉电可能残留多个 end 或 end 落在相邻行）。
- **以最后一个 end 为准**（最新写入点）。
- 确定后**清理其他所有 end 标记**——因为全机（所有盘合起来）**只能存在唯一一个 end**。
- 即：恢复流程 = 定位候选 end → 前后行校验取最后一个 → 作为真正写指针 → 抹掉其余全部 end → 从此续写。

## 2.7 录像文件内的帧记录格式（已确认）

每个 1GB 数据文件里按帧顺序写入，**先来先存**，**每 100 帧刷一次盘**（缓冲写，减少 I/O 次数），**支持音视频同步播放**。

每帧记录头 + 数据：
```
[通道序号][音频/视频标志][帧率][I/P 帧标志][帧长度][帧数据...]
```
- 通道序号：属于哪一路。
- 音频/视频：区分 AAC 音频帧 / H.264/265 视频帧。
- 帧率：用于回放定时/同步。
- I/P 帧：I 帧才在 log.txt 建索引、供 seek。
- 帧数据：压缩码流原始数据（不解码）。

## 3. RK3588 硬件加速用法
- **MPP（Media Process Platform）**：硬解 / 硬编 H.264/H.265。
- **RGA**：图像缩放、格式转换、旋转、拼接（多画面预览合成）。
- **RKNN + NPU（6 TOPS）**：人形检测等 AI 推理。
- **DRM/KMS + framebuffer**：LVGL 本地显示输出。

### 模块清单
1. **接入层 (media-input)**：RTSP 拉流、ONVIF 发现/PTZ、GB28181 SIP 信令 + PS 流解析。
2. **媒体中枢 (media-hub)**：每通道一个源，按引用零拷贝分发给录像/预览/AI，避免重复拉流。
3. **录像引擎 (recorder)**：分段（如每 30s~1min 一个 fMP4/MP4），写索引，支持连续/定时/事件录像与预录（pre-record 缓冲）。
4. **存储管理器 (storage-manager)** ⚠️：多盘分配、配额、循环覆盖、SMART 健康、热插拔、坏盘处理。细则待定（见第 5 节）。
5. **回放引擎 (playback)**：按时间轴检索、seek、倍速、导出。
6. **预览/推流 (streaming)**：WebRTC（4 用户）；本地经 MPP 解码 + RGA 合成 → LVGL。
7. **AI 分析 (analytics)**：移动侦测（VPU 运动矢量 / RGA+算法）、人形检测（RKNN）。
8. **报警/事件引擎 (event)**：汇聚移动/人形/摄像头报警 → 触发录像 + 通知 + 联动。
9. **本地 UI (ui-lvgl)**：实时多画面、回放、设置、磁盘状态。
10. **Web 后端 (web-api)**：REST + WebSocket（信令/事件推送）。
11. **数据库 (db)**：SQLite（配置、用户、事件、录像索引）。
12. **系统服务 (sys)**：日志、看门狗、时间同步、OTA 升级。
